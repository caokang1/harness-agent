# proposal.md（变更提案模板）

> 这是 OpenSpec 变更四件套的第一份。**目的：30 秒讲清"为什么做、做什么"**，给 reviewer 决策依据，**不展开技术方案**（技术方案在 design.md）。
>
> 写完后停下，等用户 review 通过再进入 design.md。

---

## Why

> 1-3 段。回答"不做这件事会有什么后果 / 谁的什么诉求被满足"。
> ⚠️ 不要写"应该"、"建议"、"为了更好"——这些是空话。要写**具体的痛点**或**具体的需求**。

例：
> 当前 X 系统中每个 Y 是独立的，用户只能做 A，无法做 B。当用户需要 C 时，不得不 D，造成 E 不必要的复杂度。引入 F 能力，让用户 G，提升 H。

## What Changes

> 用条目列出**所有要改动的范围**。粒度：每条 1 个动词 + 1 个对象，避免一条塞 3 件事。
> 这一节是 reviewer 判断"影响面是不是 SML 中的哪一档"的核心依据。

- 新增 ...
- 修改 ...
- 数据库 ... 表新增 ... 列
- 新增 ... 运行时类，作用是 ...
- ... 时自动 ...
- ... 不可见时，后端校验拒绝 ...；... 下线后 ... 静默 ...，调用时返回明确错误
- 管理后台 ... 新增 ... 按钮，复用 ... 权限
- ... 详情页展示 ...，... 添加 ... 角标
- ... 列表新增 ... 类型筛选项

## Capabilities

### New Capabilities

> 列出本次新增的能力（capability）。每条按 `<capability-name>: <一句话说明>` 写。
> capability 是 OpenSpec 的复用单元，后续其他变更可以引用。

- `<new-capability-1>`: ...
- `<new-capability-2>`: ...

### Modified Capabilities

> 列出本次修改的现有 capability。如无可删此段。

- `<existing-capability>`: ... → ...

## Out of Scope（明确不做的事）

> ⚠️ 这一节非常关键——预防 reviewer 误以为本次会做。
> 把"看起来相关但本次不做"的列清楚，并简单说为什么。

- ❌ 不做 X，因为 ...
- ❌ 不做 Y，留给后续 ...
- ❌ 不做 Z（性能优化等），等数据 ...

| 风险 | 影响 | 对策 |
|------|------|------|
| ... | ... | ... |
| ... | ... | ... |

## Scale Estimate

> 按 AGENTS.md §S/M/L 规模判定的 5 个问题自答，得出本次规模。
> 这个判定决定后续 design.md / tasks.md 的详细程度。

- 改动模块数：__（≤2 → S 提示；≥3 → M 提示；跨域 + 新抽象 → L 提示）__
- 是否引入新 API / 新表字段：__（是 → 至少 M）__
- 是否需要 subagent 分发：__（是 → L）__
- 是否需要回滚方案：__（是 → 至少 M）__
- 是否影响 cross-stack（前+后）：__（是 → 至少 M）__

**最终判定**：__S / M / L__
