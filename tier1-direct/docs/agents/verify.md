# Verify SOP — **三阶段**验证

> AGENTS.md 里保留契约摘要，完整流程与证据模板见本文件。

## 阶段一：Agent 自验（Agent 主导）

Agent 在宣布实现完成前，必须主动完成：

| 检查项 | 命令 / 证据 |
|--------|-------------|
| 编译无错误 | `bash dev.sh check --changed` |
| 架构硬规则通过 | `bash dev.sh check --arch`（基线 0 命中） |
| 测试全部通过 | `bash dev.sh test` |
| 服务启动成功 | `bash dev.sh reload` + 查看日志 |
| 改动有可观察证据（四选一即可） | HTTP 端点 curl 返回预期状态码 / 日志出现预期事件 / DB 留下可查记录 / 单元测试断言覆盖 |

**四选一的设计目的**：REST 接口可 curl，但内部逻辑改造、配置变更、schema 迁移、定时任务等不一定有 HTTP 入口，不能一刀切要求"新接口可访问"。Agent 必须明确**本次改动的可观察证据是哪一种**，并给出对应证据。

自验失败 → 先修复，不得带着已知问题进入用户验证。

## 阶段一·五：交叉 Review（M/L 规模强制）

Agent 自验通过后、进入用户验证之前，**切换角色为审查者**，执行交叉 Review。

- **S 规模**：跳过本阶段，直接进入阶段二。
- **M/L 规模**：必须完成。审查清单、产出模板、失败处理 → [`docs/agents/cross-review.md`](docs/agents/cross-review.md)。

**审查通过后**才能进入阶段二；审查不通过 → 退回修复 → 重新自验 → 复审。

---

## 阶段二：用户验证（用户主导）

Agent 自验（+ 交叉 Review，如适用）通过后**停下来**，向用户出示：

- 实现摘要（做了什么、改了哪些文件）
- 测试结果（通过 N 个，跳过/失败的原因）
- 可验证的证据清单（按自验第四项选的证据类型展开）

用户执行：

1. Review 代码
2. 按证据清单自己验证
3. 明确告知"通过"或"需要改"

**验证未通过** → Agent 修改后重新进入阶段一，再等用户复验。

## 超时 Fallback（用户长时间未回应）

- verify 期间 Agent **不得** 执行任何 `git commit` / `git push`。
- 如果用户长时间未回应（例如切换到别的任务），Agent 必须：
  1. 把当前状态写入 `.harness/progress.md`（按 `docs/agents/session.md` 进度文件模板填）
  2. 工作区保留 diff（**不** stash，不 commit），让下次会话能直接恢复
  3. 停止主动行动，等待用户回来

不要自作主张地假设"应该差不多了就提交"。

## 数据隔离

**数据源识别**：确认当前 Agent 连接的是**开发库**还是**共享环境库**，行为不同：

| 环境 | 能否破坏性操作 |
|------|---------------|
| 个人开发库（本地 / 个人 dev 环境） | **可 reset** |
| 共享/生产环境 | **禁止 reset** |

**Agent 执行 drop / truncate / reset 前必须**：先确认当前实际连接的数据源，再决定能否破坏性操作（各项目按实际配置填充具体的检查命令）。

**通用卫生规则**（不论哪套库都遵守）：

- Agent 验证写入的测试数据，**名称必须带前缀 `__agent_verify_`**。
- verify 前后运行数据快照对比（各项目按 `dev.sh` 实现），查看本轮新增了多少记录。
- 若 diff 显示 delta > 0，验证结束后必须清理带前缀的记录（或提示用户）。
