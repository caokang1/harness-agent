# 交叉 Review SOP — Agent 互审

> M/L 规模在 Agent 自验通过后、用户验证之前，强制引入第二双眼睛。

## 适用范围

| 规模 | 是否需要交叉 Review |
|------|-------------------|
| **S** | 否（改动面小、风险可控，Agent 自验 + 用户验证足够） |
| **M** | **是**（改契约/跨前后端/schema/新依赖，单 Agent 易漏结构性问题） |
| **L** | **是**（架构调整/新需求/多 subagent 并行，必须有人做整体一致性检查） |

## 为什么需要

**典型事故**：用户说"加一个查询条件"，Agent 误判为 S（只改前端），实际跨前后端应走 M。单 Agent 的"自我规模判定"存在盲区——当事人往往倾向于低估复杂度。

交叉 Review 的核心价值不是"找 bug"（测试和自验已经覆盖），而是：
1. **结构审查**：规模判定是否正确？是否遗漏了升级硬条件？
2. **架构合规**：依赖方向、接口契约、模块边界是否遵守规则？
3. **需求对齐**：改动范围是否与用户请求一致？有无过度实现或遗漏？

## 流程（三阶段验证）

```
阶段一：Agent 自验 → 阶段一·五：交叉 Review → 阶段二：用户验证
     (实现者)              (审查者)                (用户)
```

### 阶段一·五：交叉 Review（Agent B 主导）

**触发时机**：Agent A（实现者）完成自验、产出「实现摘要 + diff + 证据清单」之后，**进入用户验证之前**。

**输入**：Agent A 提供
- 实现摘要（改了什么、为什么）
- `git diff` 摘要（关键文件和行数）
- 自验结果（check/test/reload 状态）
- 规模判定依据（命中了哪个结构性条件）

**审查清单（Agent B 逐项检查）**：

| # | 检查项 | 通过标准 | 失败处理 |
|---|--------|---------|---------|
| 1 | **规模判定复审** | 命中条件与规模级别匹配，无遗漏升级硬条件 | 发现误判 → 立即停止，退回 Agent A 重新按正确规模走流程 |
| 2 | **架构合规（验收自验证据）** | Agent A 自验已附上架构检查 0 命中截图/输出；审查者**确认证据存在**，不重跑 | 证据缺失 → 退回 Agent A 补充自验输出 |
| 3 | **契约一致性**（M/L 改 API 时） | 请求/响应字段与 spec 一致；DTO/VO/Mapper 配套完整 | 不一致 → 退回 Agent A 修复 |
| 4 | **需求对齐** | 先读用户原始需求 + `tasks.md` 形成预期，再对照 diff——每一行改动都能对应到用户请求；无"顺手优化"、无过度抽象 | 发现无关改动 → 退回 Agent A 剥离或改 `[~]` 放弃 |
| 5 | **测试覆盖（验收自验证据）** | Agent A 自验已附上测试通过 N 个的输出；审查者**确认证据存在且新增逻辑有覆盖**，不重跑 | 证据缺失或新增逻辑无测试 → 退回 Agent A 补测并重新自验 |

**产出物**：

审查完成后，Agent B 在 `.harness/reviews/` 下创建 review 文件：

```markdown
## YYYY-MM-DD — <change-name> 交叉 Review

- **审查者**：Agent B
- **被审实现**：Agent A
- **规模判定**：M（改 API 契约 / 跨前后端 / schema / 依赖 / >3 文件）
- **审查结果**：通过 / 不通过（附原因）

### 逐项检查
| 检查项 | 结果 | 备注 |
|--------|------|------|
| 规模判定复审 | ✅ | 命中第 2 条（跨前后端），判定正确 |
| 架构合规 | ✅ | check --arch 0 命中 |
| 契约一致性 | ✅ | 字段与 spec 一致 |
| 需求对齐 | ✅ | 所有改动对应 tasks.md 任务 |
| 测试覆盖 | ✅ | 新增单测覆盖正常/异常路径 |

### 结论
通过 —— 可进入用户验证阶段。
```

**审查不通过的处理**：
- Agent B 明确列出问题 → Agent A 修复 → 重新进入阶段一（自验）→ 再次交叉 Review（**复审时只检查上次不通过项**）
- 禁止 Agent A 在审查不通过的情况下直接进入用户验证

## 审查者选择

### 优先路径：`requesting-code-review` skill（独立 Subagent）

调用 `requesting-code-review` skill，派遣独立 code-reviewer subagent 完成审查。subagent 从全新上下文启动，天然没有"我就是这么实现的"认知路径依赖。

> 「如果用同一个模型既写代码又 review，它容易对自己的产出视而不见——类似于人写完文章自己检查总觉得没问题。换一个架构和训练数据都不同的模型来 review，思维盲区的重叠就小得多。」

**操作**：按 `requesting-code-review` skill 步骤派 subagent，将交叉 Review 五项清单作为 checklist 一并传入：

```
WHAT_WAS_IMPLEMENTED: <实现摘要>
PLAN_OR_REQUIREMENTS: <proposal.md / tasks.md 路径>
BASE_SHA: <实现开始前的 commit；verify 前不提交，通常就是当前 HEAD>
HEAD_SHA: $(git rev-parse HEAD)（审查对象是工作区里未提交的改动：git diff BASE_SHA + git status 列出的新文件）
CHECKLIST: 规模判定复审 / 架构合规证据 / 契约一致性 / 需求对齐 / 测试覆盖证据
```

**优先使用的场景**：L 规模变更、M 规模中涉及核心业务逻辑或 API 契约变更、上一次同实例 review 发现"走过场"。

### 降级路径：同实例切换角色

不适合启动 subagent 时（如轻量 M 规模快速迭代、复审只检查上次不通过项），降级为同实例切换角色。

**已知局限**：同实例上下文里已深度嵌入"我是这么实现的"，清单第 4 项（需求对齐）最易流于形式。**必须缓解**：审查前先只读用户原始需求 + `tasks.md` 形成独立预期，再对照 diff——用"先有预期再看实现"对抗"先看实现再合理化"。

**角色切换仪式**：
1. Agent 完成实现和自验后，明确声明 `"实现完成，现在切换到审查者角色"`
2. 审查期间**不修改代码**，只产出 review 报告
3. 审查完成后，明确声明 `"审查完成，切换回实现者角色进行修复"`
