# 标准答案：怎样测出一个可信的准确率

静态扫描在新项目上一定有没见过的写法，有些会被漏掉，有些会被误报。唯一可靠的办法是：让不看扫描结果的人逐张读代码，得出答案；再用这份答案给扫描打分。这一节讲怎么做才不自欺。

## 1. 两种集合：调教集与独立核对集

| | 调教集（`kind: "tuned"`） | 独立核对集（`kind: "holdout"`） |
|---|---|---|
| 用途 | 找扫描器和配置的问题，并修复 | 衡量修复后对没见过的表的真实水平 |
| 时机 | 第一次运行后立刻做 | 所有修复完成之后才抽样、核对 |
| 成绩 | 偏乐观，因为照着它修过 | 这才是对外引用的准确率 |

某组独立核对集被用来修过扫描器后，它就变成了调教集，要在 `_meta.kind` 里改掉。对外报准确率时，需要再抽一组新的独立核对集。

**规模**：每组至少 30 张。报表多、业务域多时，按域分组，每个域一组。整个项目都不到 30 张报表时，一组覆盖全部即可，汇报时说明样本量。

**什么算"用过"一组标准答案**：只有看了这组的打分结果后再去改扫描器或配置，这组才变成调教集。第 2 步勘察时读代码修正配置，发生在任何标准答案打分之前，不影响之后建立的独立核对集。

## 2. 抽样

从上一次运行的结果里抽报表。用固定的随机种子，保证可复现：

```python
import json, random
d = json.load(open('<workspace>/runs/<run>/data.json', encoding='utf-8'))
pool = sorted(t['t'] for t in d['tables'] if t['kind'] in ('报表', '中间表') and t['st'] != '无生效写入方')
print(random.Random(20250101).sample(pool, 30))
```

- 要覆盖不同写法：实时监听写的、Job 写的、跨服务取数的都要有。
- 不要专挑扫描结果"看起来没问题"的表。
- 示例代码排除了"无生效写入方"的表，因为它们大多是废弃表，信息量小。如果要覆盖全部报表，就去掉这个条件。
- 按业务域抽样时，把 `pool` 换成某个域的表（字段 `dom`）。

## 3. 字段定义（与打分逻辑一一对应）

每张表一条记录。核对者必须按以下定义填写，否则分数没有意义：

| 字段 | 类型 | 定义 |
|---|---|---|
| `rt` | bool | 是否有**实时写入方**：存在一个未被注释的 `@KafkaListener`，从它出发（直接或经调用）会 insert、update 或 replace 这张表 |
| `jobs` | list | **非实时写入入口**。HTTP 接口填完整路径，包含类上的 `@RequestMapping` 前缀，例如 `/job/member-sales`；`@XxlJob` 填 handler 名；`@Scheduled` 或调度基类填 `类名.方法名`。只做 delete 的清理入口不算 |
| `src` | list | **直接上游表名**，不带库名。指写入这张表的那条代码路径上，在**本服务内**读到的、数据进入了写入结果或决定了写哪些行的表。包括 binlog 订阅（含经内部 topic 转发）的表，以及写入路径上 SQL 读的表。自己不算，校验日志表不算。JOIN 进来但取出的字段没有用到的表也不算 |
| `src_feign` | list | **经 Feign 的上游**：调到别的服务，在对方实现里读的**主表**。对方顺带查询的辅助表不算。没有就写空列表 |
| `ext` | list | **外部查询接口**：对外模块（config 里的 `modules.external`）中，直接读或经 Feign 间接读这张表的 HTTP 路径 |
| `int` | bool | 是否有**内部读取方**：非对外模块中有入口读这张表，而且这个入口自己不写这张表。包括别的报表的写入入口，以及订阅了这张表 binlog 的监听 |

打分规则：
- `rt` 和 `int` 比较真假。
- `jobs` 和 `ext` 按路径后缀匹配，逐条计召回。
- 上游分两档计召回：
  - **直接上游召回**：`src` 里有多少被扫描判为直接上游（binlog 订阅、转发、SQL 直接读）；
  - **直接加 Feign 召回**：`src` 和 `src_feign` 合起来，有多少被扫描找到（任一档都算）。
- `_meta.precision` 为 true 的组，还会计算直接上游的**精确率**：扫描报出的直接上游里，有多少在 `src` 或 `src_feign` 里。所以开启精确率的组，两个列表都必须写全。
- 旧格式的标准答案没有 `src_feign` 字段，把 Feign 主表也写在 `src` 里，照样能用。只是 Feign 主表会拉低直接上游召回；misses 里的 `src_found_via_feign` 会列出这些条目。

## 4. 派核对者

每批 8 到 12 张表，交给一个**独立的子代理**。子代理不继承这次对话，不知道扫描结果。几批可以并行。给它的任务说明照下面的模板写，把尖括号里的内容换掉：

```
你在核对一个 Java 微服务项目的库表血缘。只读代码，不要运行任何东西，不要修改任何文件。
不要打开 <workspace> 目录（那里有自动扫描的结果，看了会污染核对）。

仓库：<repo 路径>
表结构：<元数据 CSV 目录>（columns.csv 里有字段和注释）
对外模块（这些模块里的 HTTP 接口算"外部查询接口"）：<modules.external>
binlog 订阅的写法：<cdc 配置的一句话说明，没有就写"无">

逐张核对下面这些表：<表名列表>

每张表按这些步骤做：
1. 找出所有写这张表的 SQL：Mapper XML、@Insert/@Update 注解、MyBatis-Plus 实体（@TableName）的 insert/update/save。
   注意同名表可能在多个库里都有，按 Mapper 所在服务判断。
2. 从每个写入方法往上找调用方，一直到入口：@KafkaListener、HTTP 接口、@XxlJob、@Scheduled。
   被注释掉的监听不算。Feign 接口要跟到实现它的 Controller。
3. 在写入路径上找读取的表。只算数据进入了写入结果、或决定写哪些行的表；
   JOIN 进来但取出的字段没被用到的表不算。
   - 本服务内读的（binlog 订阅清单、SQL）写进 src；
   - 经 Feign 到对方服务读的主表写进 src_feign。
4. 找读取方：对外模块里读它的接口路径；其他模块里读它的入口。

输出一个 JSON 对象，key 是表名，value 是：
{"rt": bool, "jobs": [...], "src": [...], "src_feign": [...], "ext": [...], "int": bool,
 "evidence": {"rt": "文件:行", "jobs": {"路径": "文件:行"}, "src": {"表": "文件:行"}, "src_feign": {"表": "文件:行"}, "ext": {...}, "int": "文件:行"},
 "unsure": "拿不准的地方，没有就留空"}
每一条结论都要有 evidence；找不到证据就不要写。
```

核对者常犯的错误：
- **按 Mapper 名字猜表名**。比如名为 `UserLoginMapper` 的 Mapper，实际可能查的是另一张表。要求以 SQL 原文为准。
- **漏掉类上的 `@RequestMapping` 前缀**。
- **漏掉 Feign 实现里的查询**。

收到结果后，先抽 2 到 3 条 evidence 打开代码看一眼，有明显乱写的整批重做。

## 5. 写入标准答案文件

每组一个文件：`knowledge/truth/<序号>_<名称>.json`。

```json
{
  "_meta": {"label": "订单域 30 张", "kind": "holdout", "precision": true,
            "commit": "<核对时代码的 commit>", "reviewed_at": "2025-01-02",
            "src_exclude": {}, "_src_exclude": "经代码证实是核对时写错的上游"},
  "daily_sales": {"rt": true, "jobs": [], "src": ["orders"], "src_feign": ["order_item"], "ext": ["/admin/report/daily"], "int": true}
}
```

`evidence` 和 `unsure` 不放进标准答案文件。可以另存一份核对原始记录，放在 `knowledge/truth_raw/`，供以后复查。不要放进 `truth/`：那里每个 .json 文件都会被当成一组标准答案。

写完后用同一次运行盖章，记录核对时的代码指纹：

```bash
python S/tools/rebaseline.py <workspace>/runs/<run> --workspace <workspace>
```

以后写入这张表的代码变了，这条记录会自动标为"因代码变更未计"，不会拿过期的答案去打分。

## 6. 打分、仲裁与修复

重新运行一次。终端和 report.md 都会列出每组的成绩。`runs/<run>/evaluation.json` 的 `misses` 列出每张表差在哪里：

| 字段 | 含义 |
|---|---|
| `rt` / `int` | 标准答案的取值，扫描结果和它相反 |
| `jobs` / `ext` | 扫描没找到的入口或接口 |
| `src` | 扫描在任何一档都没找到的上游 |
| `src_found_via_feign` | 标准答案写在 `src`（直接）里，扫描只在 Feign 档找到。会拉低直接上游召回 |
| `src_extra` | 扫描报出、标准答案里没有的直接上游。只在开启精确率的组里出现 |

**每一条差异都要回代码查证**，然后归到下面三类之一：

| 结论 | 处理 |
|---|---|
| 扫描器没识别某种写法 | 按 [extending.md](extending.md) 改扫描器，然后跑 selftest |
| 配置不对或不全，比如漏了对外模块、包对应的库 | 改 `config/project.json` |
| 标准答案错了，比如按 Mapper 名猜错表、漏看了实现 | 只有拿到代码证据才能改：上游写错的，加进 `_meta.src_exclude`；其他字段直接改，并在 `accuracy_notes.json` 的 notes 里写明改了什么、为什么 |

扫描**多报**的条目只影响精确率，同样要抽查。经验上，多报里有相当一部分是核对者漏了，扫描是对的。

不要做的事：
- 为了提高分数而删减标准答案；
- 把扫描结果抄进标准答案；
- 修复后不重新抽独立核对集，就宣称准确率提高了。

修复扫描器后，先跑一遍自测，确认没有让其他组下降：

```bash
python S/tools/selftest.py --workspace <workspace> --meta-csv <元数据目录>
```

## 7. 汇报

页面"方法与准确率"里的表格会自动生成。另外要在 `accuracy_notes.json` 的 `notes` 里写清楚以下三点：

1. 独立核对集**第一次打分**时的成绩，也就是还没为它修过任何东西时的成绩；
2. 多报、漏报的主要原因，各举一个例子；
3. 标准答案本身被纠正过几处，为什么。

对用户汇报时，只引用独立核对集的数字，并说明样本量。

## 8. 维护

- **代码变了**：被标为"因代码变更未计"的条目，重新核对（可以只派一个核对者），然后执行 `rebaseline.py --tables 表名 --force`。
- **业务变化大、新增很多报表**：抽一组新的独立核对集。
