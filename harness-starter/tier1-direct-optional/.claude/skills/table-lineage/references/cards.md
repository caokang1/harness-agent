# 口径卡片、业务域、术语

扫描只能回答"谁写、从哪来、谁在读"，回答不了"这个数是什么意思、能不能用"。后者要人读代码后写下来，这就是口径卡片。卡片显示在表详情的"概览与口径"里，风险会汇总到"问题清单"。

## 卡片格式

`knowledge/cards.json`，key 是表名（不带库名）：

```json
{
  "daily_sales": {
    "role": "按天汇总全店订单数和销售额，是会员月报的上游。",
    "grain": "一天一行（day 唯一）",
    "metric": "order_count：当天每收到一条订单变更 +1；amount：订单明细 price × qty 之和，单位分。",
    "use": "看每日 GMV 趋势；月度口径用 member_sales。",
    "risks": [["订单的每次变更都会让 order_count +1，不是去重订单数。", true],
              ["store_id 列从未被写入。", false]]
  }
}
```

| 字段 | 写什么 |
|---|---|
| `role` | 一两句话：这张表回答什么业务问题，谁在用（看读取方） |
| `grain` | 一行代表什么，比如"日期 × 渠道"。从唯一索引和写入时的 where、group by 推断 |
| `metric` | 每个关键指标的**代码口径**：取哪张表的哪个字段、什么条件、怎么累加、单位。写"代码实际怎么算"，不写需求文档里应该怎么算 |
| `use` | 适合拿来做什么、不适合做什么、应该改用哪张表 |
| `risks` | `[文字, 是否已回代码确认]`。只有附了代码证据并核实过，第二项才写 true。页面上已确认的风险标红 |

以下字段由 `tools/rebaseline.py` 盖章，不要手写：
- `fp`：写入代码的指纹；
- `commit`：核对时的代码 commit；
- `reviewed_at`：核对日期。

代码变了以后，页面会提示"卡片待复核"，并列出变化的方法。

## 写卡片的流程

1. **按业务域分批**，每批 8 到 12 张，交给独立的子代理。给它的说明：

   ```
   为下面这些报表写口径卡片。只读代码，不运行、不修改任何文件。
   仓库：<repo>；表结构：<元数据目录>；表清单：<表名>
   每张表：找到全部写入代码，读懂每个字段怎么算，然后输出
   {"role", "grain", "metric", "use", "risks": [[文字, false]], "evidence": {...}}。
   风险要具体，比如可能的空指针、单位不一致、重复累加、删了不该删的数据、条件写反、和同类报表口径不同；
   每条风险附上"文件:行"和相关代码原文。不确定的写进 unsure，不要写成风险。
   ```

   页面上的写入方和上游可以给它作参考。这一步不是测准确率，不需要隔离。

2. **再派一个子代理复核风险**：逐条打开 evidence 看代码。属实的把第二项改成 true；不属实的删掉；说不清的保持 false，并在文字里注明"待确认"。

3. **合并进 `cards.json`**，然后盖章：

   ```bash
   python S/tools/rebaseline.py <workspace>/runs/<run> --workspace <workspace> --tables t1,t2
   ```

只有用户能回答的业务口径问题，比如"这个比例的分母应该是什么"，汇总起来一次性问用户。不要猜。

## 业务域：`knowledge/domains.json`

```json
{
  "domains": {"销售": ["daily_sales", "member_sales"], "库存": ["stock_alert"]},
  "descriptions": [["销售", "卖了多少、谁买的"], ["库存", "哪些商品快没货了"]],
  "reviewed_groups": {"会员月报": ["member_sales", "member_sales_v2"]},
  "rules": [["sales|refund|order", "销售"], ["stock|alert", "库存"]]
}
```

| 字段 | 作用 |
|---|---|
| `domains` | 报表和中间表人工归到哪个业务域 |
| `descriptions` | 决定总览里业务域的顺序和一句话说明 |
| `reviewed_groups` | 可选。同一域内的细分组，比如同一报表的多个版本 |
| `rules` | 新出现、还没归类的报表怎么推测业务域。先看它的上下游表属于哪个域，再按名字或注释的正则匹配。推测出来的结果在页面上标为"推测" |

业务底表不需要归类，它们按库分组，显示名来自 config 里的 `business_db_labels`。

## 术语：`knowledge/glossary.json`

```json
{
  "terms":  [["GMV", "成交总额：订单金额之和，不扣退款。", "DailySalesService.refresh"]],
  "inline": [["GMV", "成交总额：订单金额之和，不扣退款"]]
}
```

| 字段 | 作用 |
|---|---|
| `terms` | 完整的术语表：[术语, 解释, 出处]。状态码、类型值要写清楚取值和含义，出处写枚举类 |
| `inline` | 卡片和问题清单里出现这些词时，自动加虚线下划线，悬停显示解释。只放真正容易看不懂的词 |
